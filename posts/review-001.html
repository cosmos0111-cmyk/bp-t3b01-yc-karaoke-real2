Q4_K_M 양자화 PR 머지 전, 히든 딤 컷오프가 instruction following에 미치는 영향: GPU 아키텍처별 재현 조건 썰

Q4_K_M 양자화 PR, 그러니까 `ggml-backend`에 Q4_K_M 지원 추가하는 그 PR 말이다. 이거 머지 전에 아주 골 때리는 엣지케이스 하나 잡혔던 거 기억하는가? 우리 팀에서 한창 테스트 돌리고 있었는데, 유독 특정 GPU에서 instruction following 능력이 떡락하는 현상이 보고됐다. 다른 GPU는 괜찮은데 말이지. 처음엔 그냥 벤치마크 돌리다가 이상한 값 나와서 버그 리포트했지.

이게 뭐냐면, Q4_K_M은 4비트 양자화 방식 중에 제일 성능이 잘 나온다고 알려져 있잖아. 특히 FP16 대비 성능 저하가 거의 없다고. 근데 `ggml-backend`에서 Q4_K_M 지원하면서, 특정 `block_size`랑 `group_size` 조합에서 `k_quant`랑 `v_quant` 히든 딤(hidden dimension)이 의도치 않게 잘려나가는 문제가 발생하더라. 문제는 이게 FP16 모델에서는 전혀 안 나타나는 현상이고, 양자화된 모델에서만, 그것도 특정 GPU 아키텍처에서만 재현된다는 거였다.

처음에는 코드 리뷰 단계에서 놓쳤다가, QA 팀에서 문제 제기해서 알게 된 거다. 특정 NVIDIA GPU (예: RTX 3090, Ampere 아키텍처)에서는 문제가 없었는데, AMD GPU (예: RX 6800 XT, RDNA2 아키텍처)나 구형 NVIDIA GPU (예: GTX 1080 Ti, Pascal 아키텍처)에서 instruction following 관련 프롬프트에서 헛소리하거나 아예 답을 못하는 증상이 나타났다. `llama.cpp` 버전 0.8.x 대에서 주로 보고됐다.

원인은 `ggml` 내부의 `k_quant`와 `v_quant` 연산에서 발생하는 오버플로우(overflow) 문제였는데, 이게 GPU별 레지스터(register) 크기나 메모리 접근 방식 차이 때문에 특정 GPU에서만 발현되는 거였다. 마치 윈도우랑 맥에서 같은 코드 돌렸을 때 결과 다른 거랑 비슷하다고 보면 된다. 이 PR은 결국 머지되기 전에 핫픽스로 이 부분이 수정되었고, 이후 버전에서는 `ggml-backend`의 `compute_k_v_quant_dims` 함수 내부에서 `block_size`와 `group_size` 조합에 따른 히든 딤 컷오프 로직을 보다 정교하게 처리하도록 변경됐다.

이거 덕분에 `ggml-backend`의 안정성이 한 단계 올라갔다고 본다. 진짜 이런 엣지케이스 하나 때문에 모델 전체 성능이 좌우될 수 있다는 걸 제대로 보여준 사례라고 생각한다. 이런 디테일이 결국 실사용 경험을 결정짓는 거 아니겠나.
